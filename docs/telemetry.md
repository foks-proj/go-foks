# Server Telemetry (OpenTelemetry)

FOKS server daemons can export OpenTelemetry traces and metrics for every
RPC they serve, and send their logs to the same backend. It is **off by
default** and costs next to nothing when off.

## What's Recorded

Every RPC handled by a daemon (`user`, `reg`, `probe`, `kv-store`, `realtime`,
`queue`, `quota`, the `merkle-*` services, and so on) produces:

* **Metric `rpc.server.call.duration`**: a histogram in seconds, measuring
  the time from when a call is dispatched until its handler returns. Writing
  the reply back to the socket is not included. Attributes:
  * `rpc.system`: always `snowpack`
  * `rpc.service`: the protocol, e.g. `User`, `KVStore`
  * `rpc.method`: the method, e.g. `loadMe`
  * `foks.server.type`: the daemon, e.g. `User`, `RealTime`
  * `error.type`: present only on failure; the FOKS status code name,
    e.g. `AuthError`
* **A trace span** per call, named `<service>/<method>`, with the same
  attributes. Failed calls have error status and a recorded exception. The
  client doesn't send trace context, so each span starts a new trace.

Separately, everything a daemon writes to its normal log is also sent as
OTel **log records**. The same log level and sampling apply (see
`--log-level` and the `log` section of the config file). Lines logged while
serving an RPC carry that call's trace and span IDs, so a backend like
Grafana can jump between a span and its logs. The local log shows the same
IDs as a `trace` field, `{"trace_id": ..., "span_id": ...}`.

The `web` daemon serves HTTP rather than RPC, so it has no RPC metrics or
spans yet; its logs are exported like any other daemon's. Lines logged during
startup, before telemetry is set up, appear only in the local log.

## Enabling It

Telemetry is configured only through the standard `OTEL_*` environment
variables. Data is sent as OTLP over HTTP (port 4318 by default). Nothing is
exported unless an endpoint is set.

| Variable | Effect |
| --- | --- |
| `OTEL_EXPORTER_OTLP_ENDPOINT` | Base URL; turns on traces, metrics and logs, e.g. `http://otel-collector:4318` |
| `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` | Turns on traces only. Full URL, including `/v1/traces` |
| `OTEL_EXPORTER_OTLP_METRICS_ENDPOINT` | Turns on metrics only. Full URL, including `/v1/metrics` |
| `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` | Turns on logs only. Full URL, including `/v1/logs` |
| `OTEL_TRACES_EXPORTER=none` / `OTEL_METRICS_EXPORTER=none` / `OTEL_LOGS_EXPORTER=none` | Turns one signal off while the base endpoint is set |
| `OTEL_SERVICE_NAME` | Overrides the default service name, `foks-<type>` (e.g. `foks-user`) |
| `OTEL_RESOURCE_ATTRIBUTES` | Extra resource attributes, e.g. `deployment.environment=prod` |
| `OTEL_EXPORTER_OTLP_HEADERS` | Auth headers for a hosted backend, e.g. `api-key=...` |
| `OTEL_METRIC_EXPORT_INTERVAL` | Metric push interval in ms (default 60000) |
| `OTEL_TRACES_SAMPLER` / `OTEL_TRACES_SAMPLER_ARG` | Sampling, e.g. `traceidratio` / `0.1` |
| `OTEL_SDK_DISABLED=true` | Forces telemetry off |

When enabled, the daemon logs `otel stage=enabled` at startup. Export
failures are logged as warnings, to the local log only, and never affect
serving. On shutdown, pending telemetry is sent, with a 5s limit.

### Example: a Single Daemon

```sh
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 \
  foks-server user --config-path /etc/foks/foks.jsonnet
```

### Example: Docker Compose

Add an `environment` block to each FOKS service in the `docker-compose.yml`
generated by `foks-tool standup`:

```yaml
services:
  user:
    environment:
      OTEL_EXPORTER_OTLP_ENDPOINT: http://otel-collector:4318
      OTEL_RESOURCE_ATTRIBUTES: deployment.environment=prod
```

## Trying It Locally

Jaeger accepts OTLP traces directly (it doesn't take metrics, so enable
traces only):

```sh
docker run --rm -p 16686:16686 -p 4318:4318 jaegertracing/jaeger:2.5.0

OTEL_EXPORTER_OTLP_TRACES_ENDPOINT=http://localhost:4318/v1/traces \
  foks-server user ...
```

Then open <http://localhost:16686> and pick the `foks-user` service.

To get metrics and logs as well, run an
[OpenTelemetry Collector](https://opentelemetry.io/docs/collector/) and point
`OTEL_EXPORTER_OTLP_ENDPOINT` at it. From there you can forward metrics to
Prometheus, for example, traces to Jaeger or Tempo, and logs to Loki.
The all-in-one `grafana/otel-lgtm` image accepts all three directly, which is
convenient for development:

```sh
docker run --rm -p 3000:3000 -p 4318:4318 grafana/otel-lgtm

OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 foks-server user ...
```

Grafana is then at <http://localhost:3000> (login `admin`/`admin`).

A useful latency query, in Prometheus or Grafana:

```promql
histogram_quantile(0.99,
  sum by (le, rpc_service, rpc_method) (
    rate(rpc_server_call_duration_seconds_bucket[5m])))
```

## Implementation

See `server/shared/otel.go`. Handlers are wrapped when they are registered:
`ClientConn.RegisterProtocols` receives a `shared.RPCRegistrar`, which wraps
each method before passing it to the real `*rpc.Server`. Daemons don't need
any telemetry code of their own. Logs are exported through the `otelzap`
bridge, which `GlobalContext.TeeLogCore` attaches to the server's zap logger
alongside the normal output, so it stays attached when the log level or
config changes. The SDK is set up in `setupSignalsAndServe`, so in-process
integration tests always use the no-op providers.
